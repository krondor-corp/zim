## Proposal (20260524T020855Z thing5)

### Decision 1 — Role (binding pick)

**Client-side decryption of published encrypted blobs.** Sole v1 role.

Why:
- zim-hub serves ciphertext only (per T-006/T-008: hub never sees bucket secrets in plaintext). Without a WASM client, "viewer-held key" published content cannot be decoded in a browser at all.
- Aligns with thing3's `datastar-adoption-plan.md` §7 sketch — server delivers HTML shell + `/{bucket}/raw/*` ciphertext + `/assets/vendor/zim-wasm/zim_wasm.{js,wasm}`; WASM decrypts into a Datastar-injected `<div id="viewer">`.

Reserved as **out-of-scope seams** (mentioned to forestall scope creep, NOT implemented):
- Future Milkdown-style editor surface — separate task once editor route exists in zim-hub.
- IndexedDB offline cache for published-set — separate task once cache requirements are concrete.

Other (rich UI for everything): rejected. Datastar SSE handles that with no WASM dependency.

### Decision 2 — Build pipeline

**`wasm-bindgen` + `wasm-pack`** producing one `.js` glue file + one `.wasm` binary. Output vendored at:

```
crates/zim-hub/assets/vendor/zim-wasm/
├── zim_wasm.js          # ES module glue from wasm-bindgen
├── zim_wasm_bg.wasm     # the binary
└── package.json         # wasm-pack drops this; harmless, gitignore if noisy
```

Build command (documented in `crates/zim-wasm/README.md`, run manually until a `bin/build-wasm` script lands):
```
wasm-pack build crates/zim-wasm --target web --out-dir ../zim-hub/assets/vendor/zim-wasm --out-name zim_wasm --release
```

Rejected:
- `trunk` — assumes a full web app project layout; we only need the JS+WASM pair.
- Raw `cargo build --target wasm32-unknown-unknown` — no JS bindings generated; we'd hand-write `extern "C"` glue, which loses `wasm-bindgen`'s ergonomics.

No `wasm-opt` / code-splitting in v1 per T-012 acceptance.

### Decision 3 — JS interface boundary (v1)

Exported via `#[wasm_bindgen]` from `src/lib.rs`. Stable surface:

```ts
// initialise panic hook + tracing; idempotent
export function init(): void;

// load the viewer's private key for the current session.
// `handle` is whatever the hub gives the browser to identify the key
// (e.g. an opaque base64 string from a session cookie or hub fetch).
// stays in WASM linear memory; never crosses back to JS.
export function loadKeyFromSession(keyBytes: Uint8Array): void;

// decrypt one blob. envelope carries the per-blob Secret (sealed for the
// viewer's pubkey) + AEAD nonce; ciphertext is the raw bytes from
// /{bucket}/raw/*. throws on auth/tag failure.
export function decryptBlob(envelopeJson: string, ciphertext: Uint8Array): Uint8Array;

// zero the in-memory key. called on logout or tab close.
export function clearKey(): void;
```

Constraints:
- All key material stays inside WASM linear memory. JS never receives it.
- Datastar pages call these from `data-on-load` / `data-on-click` action hooks. Hub does not import zim-wasm server-side.
- Envelope format = JSON serialisation of T-008's published envelope (drives a coordination touchpoint with whoever takes T-008's publish-envelope design).

### Decision 6 — Reuse from other Zim crates

- `zim-crypto` (binding dependency): needed for `Secret`, `SecretShare`, `PublicKey`/`SecretKey`. **Requires a `wasm` cargo feature** that excludes the `iroh` dependency. `iroh` pulls in networking/runtime that almost certainly will not compile to `wasm32-unknown-unknown` cleanly. Two shapes for thing1 to pick:
  - **(a) Recommended:** `zim-crypto` adds `[features] default = ["iroh-keys"]; iroh-keys = ["dep:iroh"]; wasm = []`. The `PublicKey`/`SecretKey` re-exports from iroh become `#[cfg(feature = "iroh-keys")]`. zim-wasm uses raw `ed25519_dalek::SigningKey` / `x25519_dalek::StaticSecret` directly.
  - (b) Split `zim-crypto-core` with the dalek + chacha + blake3 primitives only; current `zim-crypto` re-exports it plus the iroh wrappers. Bigger touch.
- `zim-fs` / `zim-store` / `zim-protocol` / `zim-peer`: **none of these for v1.** SQLite is server-side. Filesystem is server-side. Protocol/peer are network-side. WASM only handles decryption of bytes the hub already fetched.

## Envelope-schema update (20260524T031821Z thing5)

thing2 sent T-008 coordination note (20260524T024508Z) flagging that the v1 envelope needs a tagged union to be non-breaking when the public-viewer path lands. Applied:

```rust
#[serde(tag = "kind", rename_all = "lowercase")]
enum Envelope {
    Public { secret: String },   // T-008: hex per-blob Secret; no session key
    Sealed { share:  String },   // T-001: SecretShare hex; needs loadKeyFromSession
}
```

Both branches implemented in `crates/zim-wasm/src/lib.rs` (`decryptBlob` dispatch). Added `hex = "0.4"` dep for the public branch's hex decode. README.md updated with the schema. JS surface unchanged (`decryptBlob(envelopeJson, ciphertext)` still the only entry point).
