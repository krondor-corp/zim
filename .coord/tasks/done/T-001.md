## Proposal (20260524T050253Z thing5)

### Headline pattern — Hub is an **identity key vault**, not a custodian

zim-hub stores **encrypted blobs of per-viewer private keys**, indexed by Google identity. **Unlock happens client-side in the browser** (via zim-wasm + Argon2id). Plaintext keys never exist server-side. The hub server can be fully compromised without leaking any viewer's secret — the worst-case attacker gets ciphertext + Google identities, but needs each user's password to decrypt.

This pattern means:
- The hub cannot decrypt sealed envelopes on the user's behalf — only the user's browser can.
- Hub operator (even a malicious one) cannot serve content as if they were a viewer.
- Per-T-006 + T-016: hub-as-mirror peer never holds any **bucket** secret; this design adds that hub-as-key-vault never holds any **viewer** secret either.
- The trust surface collapses to **the JS bundle served by the hub** — see threat model.

### Decision 1 — Identity flow (end-to-end)

**Enrolment (first-time user):**
1. Viewer hits zim-hub. No session cookie. Hub renders `/login` with "Sign in with Google".
2. Standard OAuth2 PKCE: hub redirects to Google, gets back an `id_token` + `access_token`. Hub verifies `id_token` signature against Google's JWKS and extracts `sub` (Google subject ID — stable per-account opaque string).
3. Hub establishes signed-cookie session (axum-extra `SignedJar` or `tower-cookies` — same crate either way) keyed by `sub`.
4. Hub looks up `(encrypted_blob, salt)` by `sub` in its `identity_keys` SQLite table. **Not found** → render `/enrol` page.
5. Viewer's browser: zim-wasm's new `generateKey()` makes a fresh ed25519 keypair in WASM linear memory and returns the public key.
6. Browser prompts viewer for a new unlock password + confirm.
7. zim-wasm's new `encryptKeyBlob(password)` derives a 32-byte KEK via Argon2id (per-blob random salt, 16 B), encrypts the in-memory ed25519 secret with ChaCha20-Poly1305 (matches the rest of Zim's AEAD choice), and returns `{encrypted_blob, salt, public_key}`.
8. Browser POSTs `(encrypted_blob_hex, salt_hex, public_key_hex)` to hub's `/api/v0/identity/enrol`. Hub inserts the row keyed by `sub`.
9. Browser calls `zim_wasm.loadKeyFromSession(secretBytes)` — secret is already in memory from step 5; the new helper just confirms session state.
10. Hub displays viewer's `public_key` hex with a "send this to the bucket owner so they can authorise you" copy-button. Out-of-band: owner runs `zim viewer authorize <pk>` on the owner node (T-001c sub-task) to add this pk to the bucket's shares (encrypts per-blob `Secret`s for this pk, appends new manifest entry).

**Login (returning viewer):**
1. Viewer hits zim-hub. Maybe has session cookie (still in OAuth window), maybe not.
2. If no cookie: Google OAuth flow as steps 1–3 above. If cookie: jump to 3.
3. Hub fetches `(encrypted_blob, salt)` by `sub`. **Found.**
4. Hub renders `/unlock` (Datastar page): single password input + Datastar action that fetches the blob and calls zim-wasm `unlockKeyBlob`.
5. Browser GETs `/api/v0/identity/blob` → `{encrypted_blob_hex, salt_hex}`.
6. Browser calls zim-wasm `unlockKeyBlob(blob_bytes, salt_bytes, password)`. WASM Argon2-derives KEK, ChaCha20-decrypts blob → 32-byte ed25519 secret in `SESSION_KEY` thread-local. On auth-tag failure, returns a `JsError` and the page re-renders the form with "wrong password".
7. Browser is now in "unlocked" state — sealed-envelope `decryptBlob` calls work for any blob whose `SecretShare` was sealed for this viewer's pubkey.

**Logout:**
1. Viewer hits "Log out" — Datastar action calls `zim_wasm.clearKey()` (zeroes thread-local) and POSTs `/api/v0/identity/logout`.
2. Hub clears session cookie. Encrypted blob row stays in the table (so login works again with the same password).

**Password change:**
1. Browser is unlocked. Viewer hits `/account/password`.
2. Browser prompts for new password + confirm.
3. zim-wasm `encryptKeyBlob(new_password)` re-encrypts the in-memory secret with fresh KEK + fresh salt.
4. Browser POSTs `(new_blob, new_salt)` to `/api/v0/identity/rekey`. Hub UPDATE's the row by `sub`.

**Key rotation** (compromise recovery):
1. Browser is unlocked. Viewer hits `/account/rotate`.
2. zim-wasm `generateKey()` makes a fresh keypair.
3. Browser shows old + new pubkey: "ask the owner to deauthorise the old key and authorise the new key".
4. Once owner confirms (out-of-band, via `zim viewer authorize/deauthorise`), browser re-encrypts with current password + POSTs to `/api/v0/identity/rotate { new_blob, new_salt, new_public_key }`. Hub updates the row.
5. Future logins use the new key.

### Decision 2 — Local credential state (hub-side schema)

```sql
CREATE TABLE identity_keys (
    google_sub      TEXT    PRIMARY KEY,        -- Google `sub` claim (stable per account)
    google_email    TEXT    NOT NULL,           -- denormalised from id_token for display + owner-side recognition
    public_key      TEXT    NOT NULL,           -- ed25519 pubkey hex (32 bytes -> 64 hex)
    encrypted_blob  BLOB    NOT NULL,           -- ChaCha20-Poly1305 ciphertext of the ed25519 secret (nonce-prepended per zim-crypto Secret format)
    salt            BLOB    NOT NULL,           -- Argon2id salt, 16 bytes
    kdf_params      TEXT    NOT NULL,           -- JSON: {m_cost, t_cost, p_cost, alg: "argon2id", version: 19}
    created_at      INTEGER NOT NULL,           -- unix seconds
    last_used_at    INTEGER NOT NULL,           -- unix seconds; refreshed on successful unlock
    UNIQUE(public_key)
);

CREATE INDEX idx_identity_keys_public_key ON identity_keys(public_key);
```

`kdf_params` is stored as a JSON string so we can upgrade Argon2 parameters (e.g. raise `m_cost` over time) without a schema migration — on next password change, blob gets re-encrypted with new params.

**Session cookie:**
- Axum signed-cookie containing `{ sub, exp: <now+24h> }`.
- Signing key: 32-byte random, persisted in hub's data dir at `data_dir/session.key` (auto-generated on first start, plaintext file with 0600 mode).
- 24-hour expiry. Refreshed on each authenticated request.

**Notably NOT stored:**
- Google `id_token` past the OAuth callback (only `sub` + `email` extracted and persisted).
- `access_token` / `refresh_token` — we don't need long-lived Google access; auth is one-shot at session-start.
- Password (ever — only Argon2-derived KEK transient in WASM memory).
- Plaintext ed25519 secret (ever, server-side).

### Decision 3 — Remote peer authorization

Two flows: hub-peer's own identity vs. viewer key authorization.

**Hub-peer identity** (unchanged from current zim-peer behaviour):
- Hub's embedded peer (per T-015) has its own iroh `SecretKey` at `data_dir/peer.key.pem` (renames from current `key.pem`). Generated on first start, plaintext on disk. This is the hub's network identity.
- Bucket owner adds this pubkey to `manifest.mirrors` via `zim mirror add <hub-pk>` (per T-016c).
- Hub's peer can now sync as a Mirror peer-type (per T-016 Decision 1).
- **Not affected by Google auth.** Hub's own peer key is operator-side, not viewer-side.

**Viewer key authorization** (new):
- Viewer enrols via Google → hub stores `(google_sub, public_key)` mapping + encrypted blob.
- Hub exposes a read-only API for the owner: `GET /api/v0/identity/pending` returns a list of viewers (email + pubkey hex) that have enrolled but are not yet in any of the owner's bucket `manifest.shares`. Owner can see who wants in.
- Owner side (T-001c): `zim viewer list-pending --hub <url>` calls the hub API, prints the list. `zim viewer authorize <pk> --bucket <id>` adds the pubkey to the bucket's `manifest.shares` (signs + appends manifest entry, encrypts the bucket's per-blob `Secret`s for the new viewer, appends sealed shares to relevant entries' `published_set` records — or wherever T-008 lands the per-entry secrets).
- Mirror peer subsequently syncs the new manifest version → hub picks up that the viewer is now authorised. Viewer's `decryptBlob` calls now succeed for sealed envelopes targeted at them.

**Owner-approval is out-of-band.** The hub does not auto-approve viewers. Decision rationale: even with strong identity verification (Google), the owner is the one who controls the bucket — auto-approval would let anyone with a Google account into the bucket.

### Decision 4 — Key unlock crypto

| Step | Algorithm | Library | Notes |
|---|---|---|---|
| Key derivation (password → 32-byte KEK) | **Argon2id** | `argon2 = "0.5"` (pure Rust, WASM-clean) | Initial params: `m_cost = 19456 KiB (~19 MB), t_cost = 2, p_cost = 1` (OWASP recommendation as of 2024; same as Bitwarden defaults). Stored in `kdf_params` JSON. |
| Blob encryption | **ChaCha20-Poly1305** | `chacha20poly1305 = "0.10"` (already in zim-wasm via zim-crypto) | Reuses `zim_crypto::Secret` wire format: 12-byte nonce prepended to ciphertext. **Important**: `Secret::encrypt` already does this — we can just wrap the KEK in a `Secret` and call `Secret::encrypt(secret_key_bytes)`. No new crypto code needed in zim-crypto. |
| Salt | 16 random bytes, generated browser-side via WebCrypto / `getrandom` (already wired for WASM via the T-012 `wasm_js` cfg). | | One per blob. Public — stored alongside ciphertext. |

The KEK derivation in pseudo-Rust (zim-wasm):
```rust
let argon2 = Argon2::new(
    argon2::Algorithm::Argon2id,
    argon2::Version::V0x13,
    argon2::Params::new(19456, 2, 1, Some(32)).unwrap(),
);
let mut kek = [0u8; 32];
argon2.hash_password_into(password.as_bytes(), &salt, &mut kek).unwrap();
let kek_as_secret = Secret::from_slice(&kek)?;
let plaintext_secret_key = kek_as_secret.decrypt(&encrypted_blob)?;
```

Reusing `zim_crypto::Secret` for the wrapping means we don't introduce a second AEAD implementation. The "Secret" name is a slight overload — it's a per-blob symmetric key in bucket context, and a per-user-derived KEK in identity-vault context — but the wire format is identical and that's the property we want.

### Decision 5 — Threat model

| Adversary | Capability | Mitigation | Residual risk |
|---|---|---|---|
| **Network observer** (CDN, ISP, hostile WiFi) | TLS metadata only | TLS 1.3 mandatory (axum's defaults); HSTS header set by hub. | None for crypto; metadata observability is inherent. |
| **Compromised hub server** (full root) | Read DB → has all encrypted blobs + Google identities. Read TLS keys → MITM future sessions. | Cannot decrypt blobs without per-user passwords. Cannot impersonate viewers in protocol because viewer-key never leaves browser. | **Critical**: attacker can replace the served JS/WASM bundle with a phishing variant that exfiltrates passwords on unlock. **Mitigation**: SRI hashes on `<script>` tags for `zim_wasm.js` and `datastar.min.js` (computed at build time, baked into `base.html` template); strict CSP `script-src 'self'`; viewers should verify the hub's TLS cert pinning if paranoid. Document this in the wiki under "trust assumptions". |
| **Compromised Google account** | Phisher gets victim's Google session → can log into zim-hub as victim. | Phisher then sees the encrypted blob — but needs the unlock password. Password is a second factor beyond the Google account. | If victim uses the same password for Google and for zim-hub unlock, single-credential compromise. Mitigation: docs say "use a distinct unlock password, not your Google password". |
| **Hub operator** (owns the hub, want to read viewer content) | Can see DB + can modify served JS. | Same as compromised server — cannot decrypt without passwords; can phish via swapped JS. | SRI + CSP as above. Operator-side viewer audit: viewer can copy their own pubkey from `/account` and compare to what the owner sees via `zim viewer list-pending` — pubkey mismatch = swapped key. |
| **Bucket owner** (legitimate, but their owner-key is compromised) | Can decrypt all bucket content. | Out of scope — owner compromise = full bucket compromise by design. | T-001 doesn't change the owner-side threat model. |
| **Brute force password attack** (against stolen blob) | Argon2id with 19 MB memory cost makes GPU/ASIC attacks 100x–1000x more expensive than scrypt or bcrypt. | Recommend ≥16-char passwords in enrolment guidance. Rate-limit unlock attempts client-side (cheap to bypass) and at the hub's `/api/v0/identity/blob` endpoint (effective). | Weak passwords are weak. Documented. |
| **Compromised viewer browser** (malicious extension, keylogger) | Reads in-memory key. | Out of scope — fully-owned browser = game over. | Document "use a clean browser profile for sensitive buckets". |

**The single load-bearing trust assumption**: viewer trusts the JS+WASM bundle served by zim-hub. Mitigation: SRI hashes baked into HTML templates against pre-computed bundle hashes, plus CSP `script-src 'self'`. Future hardening: separate the JS bundle delivery (vendored, audited, version-pinned) from the hub-rendered HTML, so JS changes require a deliberate vendor-bump commit (already the case for `datastar.min.js`; same pattern for `zim_wasm.js`).

### Decision 7 — Out of scope (explicit non-goals)

- Multi-IdP support — Google only for v1. Apple / GitHub / Microsoft can be added in a follow-up by parameterising the OAuth provider; no design change required.
- Password recovery — **explicitly no recovery mechanism**. Lost password = lost key = owner must deauthorise the old pubkey and the viewer re-enrols with a new keypair. Documented as a hard property in the wiki. Alternatives (escrow, social recovery) were considered and rejected for v1: they'd require either a custodian (defeats the design) or extra ceremony that doesn't fit the "deploy one binary, sign in via Google" pitch.
- Hardware-key (WebAuthn / FIDO2) unlock — interesting future direction; would replace the password-derived KEK with a hardware-attested KEK. Out of v1 scope.
- Per-bucket viewer authorisation (vs per-hub-tenant) — viewer's pubkey is authorised per-bucket by the owner. A viewer who's authorised on bucket A is not implicitly authorised on bucket B. This is the existing zim-fs `manifest.shares` semantics; T-001 just adds Google identity → pubkey mapping. No change needed.
- Federated hubs (multiple zim-hubs sharing identity stores) — explicit non-goal; each hub is its own identity vault.
