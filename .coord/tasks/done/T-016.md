## Goal
The T-006 removal of `PrincipalRole::Mirror` was right at the **role-enum-on-Principal** layer (we don't need Mirror in the share/membership model — T-008 handles publish access via the per-entry secrets). But the protocol still needs to identify a peer as a **mirror peer**: a non-member peer that holds blobs and serves the published-set, without holding the bucket secret.

User direction: "we should not have gotten rid of mirrors because zim-hub needs to act like one." Decode: zim-hub IS a mirror peer; we need the protocol-level notion back, just at the peer-identification layer, not the principal-role layer.

## Design questions to answer

- [ ] **Peer identity vs principal identity**: today a `Principal` is the per-bucket membership identity. A "mirror peer" is identified by its peer key (iroh public key) and has no bucket-principal mapping. Document the two-layer model: principal = bucket membership (Owner only now), peer-type = wire-level identification (Member, Mirror, Anonymous?).
- [ ] **Wire protocol verbs**: what verbs can a mirror peer call? Probably `fetch_manifest`, `fetch_blob_by_link` (for blobs referenced in published_set), nothing else. Document the set.
- [ ] **Owner-side gating**: when a source peer sees an incoming sync request from an unidentified peer, how does it decide if/how to serve? Mirrors get the manifest (public artefact anyway) + blobs referenced by published_set. Non-mirror non-members get nothing (or just the manifest).
- [ ] **Mirror identity announce**: how does zim-hub tell the source peer "I am a mirror, serve me the published-set blobs"? Could be:
  - (a) Owner explicitly adds the mirror's peer key to a `mirrors: Vec<PublicKey>` field in the manifest. Pre-authorized.
  - (b) Anyone presenting the manifest is implicitly trusted to fetch published-set blobs (manifest is public; published_set entries name the blobs; if you have the manifest you already know what to ask for).
  - Pick one with rationale.
- [ ] **Touchpoint list**: what protocol code needs to learn the mirror-peer concept? (zim-protocol's handshake / sync / blob-serve paths.)
- [ ] **No `PrincipalRole` enum revival** — keep T-006's clean break at the principal layer. The mirror concept lives at the peer/network layer.

## Proposal (20260524T044750Z thing5)

### Decision 1 — Two-layer identity model

Today, `PrincipalRole` collapses two unrelated concepts into one enum:

| Layer | Concept | Identity key | Lives in |
|---|---|---|---|
| **Principal** (bucket membership) | "who is authorised to read/write this bucket's plaintext?" | per-bucket entry keyed by `PublicKey` in `Manifest.shares` | `crates/zim-fs/src/fs/manifest.rs` |
| **Peer-type** (network role) | "what is this peer's relationship to this bucket on the wire?" | this peer's iroh `PublicKey` | `crates/zim-fs/src/fs/manifest.rs` (new `mirrors` field) + `crates/zim-protocol/src/peer/**` (gating) |

After T-006a lands, the principal layer collapses to a single role: **Owner**. There is no "principal role enum" anymore; if you have a `Share` in `manifest.shares`, you are an owner of that bucket. End of layer.

The peer-type layer is new — or rather, finally distinguished. Variants:

```rust
/// Peer-type as derived from the bucket's manifest at sync time.
/// NOT a stored field — derived per-(peer, bucket) at gating time.
pub enum PeerType {
    /// Peer key appears in `manifest.shares` — bucket owner. Sees HEAD; gets full sync.
    Owner,
    /// Peer key appears in `manifest.mirrors` — pre-authorised mirror. Sees `latest_published`; gets manifest + log-head + blobs referenced by `published_set`.
    Mirror,
    /// Peer key appears in neither. Default-deny: serves manifest only (it's public), no blobs.
    Anonymous,
}
```

`PeerType` is derived per-bucket per-incoming-peer-key, not stored. There is no `PeerType` field anywhere — it's the output of a `Manifest::classify_peer(peer_pk) -> PeerType` lookup.

This preserves T-006's clean break: no role enum on `Principal`. The mirror concept moves up to a peer-key list (`Vec<PublicKey>`) on the manifest.

### Decision 2 — Wire protocol verbs available to each peer-type

Verb set, gated by `PeerType`:

| Verb | Owner | Mirror | Anonymous |
|---|---|---|---|
| `fetch_manifest` | ✅ | ✅ | ✅ (manifest is a public artefact — hashes, shares-map structure, mirrors list — no plaintext) |
| `fetch_log_head` (current head link + height) | ✅ | ✅ | ❌ (avoids revealing write cadence to unauthorised observers) |
| `fetch_blob_by_link` for `link ∈ manifest.shares.*.encrypted_blobs` (HEAD branch) | ✅ | ❌ | ❌ |
| `fetch_blob_by_link` for `link ∈ Fs::load(latest_published).published_set` | ✅ | ✅ | ❌ |
| `append_log_entry` (write) | ✅ | ❌ | ❌ |
| `add_share` / `add_mirror` (membership / mirror-list mutation) | ✅ | ❌ | ❌ |
| iroh-blobs ALPN raw fetch (`iroh_blobs::ALPN`) | gated by per-blob link check against the same rules above | | |

**Important**: blob fetches via the iroh-blobs raw protocol need the same gating. Today `router_builder.accept(iroh_blobs::ALPN, inner_blobs)` in `peer/mod.rs:42` accepts blob requests unconditionally. T-016 must add a gating layer: when an incoming blob fetch arrives, check `PeerType` against the link before serving. (Sub-task spawned below.)

### Decision 3 — Owner-side gating logic

Connection-time:

```rust
// In handle_connection (peer/protocol/mod.rs:34) or the per-bucket sync path:
let sender_pk: PublicKey = conn.remote_node_id()?.into();
let peer_type = manifest.classify_peer(&sender_pk);
// Dispatch using peer_type to choose which verbs/blobs to serve.
```

`Manifest::classify_peer` (new helper, lives in `zim-fs/src/fs/manifest.rs`):

```rust
impl Manifest {
    pub fn classify_peer(&self, pk: &PublicKey) -> PeerType {
        if self.shares.contains_key(&pk.to_hex()) { return PeerType::Owner; }
        if self.mirrors.iter().any(|m| m == pk) { return PeerType::Mirror; }
        PeerType::Anonymous
    }
}
```

Sync-side: `Peer::mount_for_read` (currently `peer_inner.rs:317`) loses its `PrincipalRole` match arm and instead does:

```rust
let peer_type = manifest.classify_peer(&self.secret_key.public());
match peer_type {
    PeerType::Owner   => self.mount(bucket_id).await,        // HEAD
    PeerType::Mirror  => self.mount_at_latest_published(bucket_id).await,  // existing latest_published path
    PeerType::Anonymous => Err(FsError::NotAuthorized),
}
```

Bonus: this lets the mount layer ditch its `use zim_fs::PrincipalRole` import — clean separation finally lands.

### Decision 4 — Mirror announcement mechanism — **(a) Explicit `mirrors: Vec<PublicKey>` on the manifest**

Picking **(a)** over implicit-trust:

**Rationale for explicit:**
- **Revocation possible.** Owner removes a peer key from `mirrors`, signs a new manifest entry, next sync drops them. With implicit trust, a hostile mirror who once grabbed the manifest can keep mirroring forever.
- **Audit trail.** `manifest.mirrors` is a signed list. Anyone reading the manifest can verify which peers the owner authorised to mirror. Implicit trust gives zero visibility.
- **Side-channel attacks contained.** Mirrors learn read patterns (which encrypted blobs get fetched). A hostile or compromised "free-rider" mirror could correlate viewer fetches against published_set entries. Explicit list bounds this surface.
- **Matches user intent.** "I want zim-hub to mirror my bucket" is a deliberate act by the owner. Adding the peer key once at deploy time is the right ergonomic cost.

**Cost of explicit:**
- One new field on `Manifest`: `mirrors: Vec<PublicKey>` (signed under the existing log).
- One new mutation verb: `Manifest::add_mirror(pk)` / `Manifest::remove_mirror(pk)`.
- One new CLI/HTTP surface point on `zim-peer` (owner side): `zim mirror add <pk>`, `zim mirror remove <pk>`, `zim mirror list`.
- zim-hub deploy story: on first launch, hub prints its peer key; operator runs `zim mirror add <hub-pk>` on the owner node. One-shot.

**Implicit-trust path explicitly rejected.** Even with the manifest being public, implicit trust grants serving rights to anyone presenting the manifest, which makes the bucket owner unable to control who runs an unauthorised mirror. The `published_set` is supposed to be the public-read surface; the mirror list is the trust surface.

### Decision 6 — Explicit non-revival of `PrincipalRole`

Confirmed: T-016 does **not** re-introduce a `PrincipalRole` enum, nor any per-principal role concept. The mirror identification is a peer-key list (`Vec<PublicKey>`) on the manifest, not a role tag on a principal. T-006a's clean break stays clean.

The transient `PeerType` enum introduced in Decision 1 is **derived, not stored** — it's never serialised, never lives in a `Share` or `Principal`, never has a `Display` impl that ends up in API responses. It exists only as a control-flow type at the gating layer.
