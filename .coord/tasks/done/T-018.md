## Goal
Let users register a real filesystem path as a backup target for a bucket. The daemon manages the sync: on each new commit, diffs the tree and materializes only changed files to the target directory. User controls the backup directory; Zim provides incremental, decrypted, browsable snapshots. Part of a 3-2-1 backup strategy — fault tolerance against Zim itself (if blob store or SQLite corrupts, user has a real filesystem copy).

## Design

### Storage
New `sync_targets` table in the daemon's SQLite DB (same pattern as FUSE mounts):

```sql
CREATE TABLE sync_targets (
    id          TEXT PRIMARY KEY,        -- uuid
    bucket_id   TEXT NOT NULL,
    target_path TEXT NOT NULL,           -- real filesystem path chosen by user
    last_head   TEXT,                    -- Link of last-synced manifest head (null = never synced)
    created_at  INTEGER NOT NULL,
    last_sync   INTEGER,                -- unix seconds of last successful sync
    status      TEXT NOT NULL DEFAULT 'active'  -- "active" | "paused" | "error"
);
```

### CLI surface (mirrors FUSE mount pattern)
- `zim bucket sync add <bucket_id> /path/to/backup` — register target; immediate first sync.
- `zim bucket sync remove <bucket_id>` — unregister (does NOT delete the backup directory).
- `zim bucket sync list` — show targets with last-synced head, last sync time, status.
- `zim bucket sync now <bucket_id>` — force immediate sync (bypass waiting for next commit).
- `zim bucket sync pause/resume <bucket_id>` — toggle without removing.

### HTTP API
- `POST /api/v0/bucket/sync/{add,remove,list,now,pause,resume}` — matching the CLI surface.

### Daemon service
`SyncService` implementing `zim_runtime::Service`. On startup:
1. Load all `active` sync targets from DB.
2. For each, check if `last_head` matches current bucket head. If not, sync immediately (catch up).
3. Subscribe to bucket commit stream (same event channel that drives the sync protocol).
4. On new commit → for each sync target on that bucket: diff `last_head` vs `new_head` → materialize changes → update `last_head` + `last_sync`. Error → set `status = "error"`, log, retry on next commit.

### Sync logic (the diff + materialize)
- Walk old head tree and new head tree in parallel (both are content-addressed Merkle trees in zim-fs).
- Compute: added files, modified files (Link changed), deleted files, renamed directories.
- For each added/modified file: fetch blob from store → decrypt with NodeLink::Secret → write to `target_path/<relative_path>`.
- For each deleted file: `fs::remove_file(target_path/<relative_path>)`.
- For directory structure changes: `fs::create_dir_all` / `fs::remove_dir` as needed.
- First sync (last_head = null): materialize entire tree.
- Store `.zim-sync` dotfile in target dir root with `{ bucket_id, last_head, last_sync }` as a secondary consistency check.

### Reuse from FUSE
The FUSE implementation (`crates/zim-peer/src/fuse/`) already walks the tree and decrypts per-node. The tree-walking + decrypt logic should be shared (factor into a common helper in zim-fs or a shared module in zim-peer) rather than duplicated. The output differs: FUSE serves via kernel VFS callbacks; backup writes to real files.

## Out of scope
- Encrypted backup (backup is decrypted, browsable files — that's the point for fault tolerance against Zim).
- Remote backup targets (S3, rclone, etc.) — v2; v1 is local filesystem.
- Conflict resolution (one-way sync: bucket → filesystem, never the reverse).
- Backup verification / integrity checking (future — compare backup dir against head).
- Continuous real-time sync with inotify/fsevents (v2; v1 syncs on commit events).

### Design summary (for audit)

**Storage**: `sync_targets` SQLite table mirroring the `fuse_mounts` pattern. One row per registered backup target. Columns: id (uuid), bucket_id, target_path (unique), last_head (nullable Link hex), last_sync (unix seconds), status (active/paused/error), error_message, timestamps.

**Poll loop**: `BackupSyncService::run` uses `tokio::select!` with `shutdown_rx.changed()` vs `tokio::time::sleep(30s)`. Each poll: load all `status = 'active'` targets → for each, compare `peer.logs().head(bucket_id)` hash string against `last_head` → if different (or first sync), call `sync_to_disk` → update `last_head` + `last_sync` on success, set `status: error` on failure.

**Materialization (v1)**: full tree dump on every sync. `sync_to_disk` calls `peer.mount(bucket_id)` to get the decrypted `Fs`, writes a `.zim-sync` JSON marker file, then `materialize_tree` recursively walks via `Fs::ls(path)` — for data nodes calls `Fs::cat(path)` and writes bytes to `target_dir/<relative_path>`, for directories calls `create_dir_all` and recurses.

**Shutdown**: the service is a named handle on `ShutdownHandle`; SIGINT/SIGTERM cancels the `tokio::select!` sleep branch and the service returns cleanly.

### Documented follow-ups (NOT in v1)

1. **Incremental tree-diff**: v1 does a full dump on every head change. A proper diff would walk old-head and new-head trees in parallel, compute added/modified/deleted files, and only touch changed paths. This is the FUSE-shared tree-walk code the acceptance criteria mention. Blocked on T-019 (zim-core `BlobStore` trait) for clean abstraction.
2. **`sync now` CLI/HTTP**: force-immediate-sync endpoint. The model + route are trivial (set `last_head = null` to force next poll to trigger); just not wired yet.
3. **Shared tree-walk with FUSE**: the FUSE implementation in `fuse/fuse_fs.rs` has its own tree traversal. Both should share a common `walk_tree(mount, visitor)` helper. Deferred to after T-019 lands the `BlobStore` trait.
4. **Event-driven sync**: replace poll with `broadcast::Sender<Event>` subscription (thing2's P-6). When the event channel ships, the SyncService subscribes to `Event::ManifestChanged { bucket_id }` instead of polling.
