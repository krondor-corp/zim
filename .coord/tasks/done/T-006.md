## Proposal (20260524T014300Z thing2)

### Current shape
- Two-variant enum `mount::PrincipalRole { Owner, Mirror }` (crates/common/src/mount/principal.rs).
- Roles are honour-system; principal.rs:11 explicitly states "There is no cryptographic enforcement of roles."
- `Owner` shares hold an X25519-encrypted bucket secret; `Mirror` shares hold no secret.
- `Manifest::publish(secret)` writes the plaintext bucket secret into `Manifest::public` (mount/manifest.rs:378). Any peer holding the manifest can then decrypt — Mirror membership is not required to read published content.
- `Mount::add_mirror`, `MirrorCannotMount`, and the `match our_role` branch in `peer_inner.rs:336` exist solely to model the "I am listed as Mirror, only show me published content" pattern.
- Public surface that names Mirror: HTTP `POST /buckets/{id}/share { role: "mirror" }`, CLI `bucket shares create --role mirror`, dev fixture `node2 = mirror`, docs referencing Mirror in concepts/overview, PATTERNS, INSTALL, DEBUG, API, SUCCESS_CRITERIA.

### Target shape
Single role. Drop the enum entirely; collapse `Principal` to `{ identity }`.

- `mount::Principal { identity: PublicKey }` — no `role` field.
- `Share` always carries an encrypted secret (no `new_mirror` constructor; no `None` share variant).
- A peer that wants read-only access to a published bucket fetches the manifest + blobs as a non-member and decrypts via `Manifest::public` (which already supports this). It is not added to the share map.
- `zim-hub` (T-002 successor crate) is the only "read-only mirror" surface; it runs as a non-member peer that reads the published secret. No protocol role is required to model it.
- `publish` / `unpublish` semantics are unchanged: writes/clears `Manifest::public`. They become a property of the bucket, decoupled from membership.

### Protocol message/permission set (target)
- Membership ops: `add_principal(identity, share)`, `remove_principal(identity)`. Both require requester to be a member with a valid Share for the prior manifest version.
- Bucket ops: `publish(secret)`, `unpublish()`, `commit(new_head)`. All require requester to be a member.
- Sync ops: blob fetch / pin announce — unauthenticated, content-addressed.
- That's the whole permission surface. There is no Mirror gate, no published-only mount path, no role check in `bidirectional` protocol.

## Proposal v2 (20260524T015026Z thing2) — granularity moves to nodes

Product direction update (verbal): bucket-level "public" is removed. `Manifest::public` / `publish` / `unpublish` go away. Granularity for public-ness moves to individual nodes. Shares are reworked to **point at a node** and are **persisted in the manifest**.

This is cleaner than v1: the data model already has per-node secrets (`NodeLink::Data(_, Secret, _)` and `NodeLink::Dir(_, Secret)` in `mount/node.rs:96-99`), so per-node keys aren't new — only the share primitive changes.

### Target shape v2

**One share type, generalised:**

```rust
pub struct Share {
    /// Which node's secret this share grants access to.
    /// Root share = whole-bucket access. Subtree share = scoped access.
    target: NodeRef,           // Link/CID of the target node
    /// How the node's secret is wrapped.
    wrap: ShareWrap,
}

pub enum ShareWrap {
    /// Encrypted to a specific identity (X25519). Grants that identity access.
    Sealed { recipient: PublicKey, ciphertext: SecretShare },
    /// Plaintext. Anyone with the manifest can decrypt this node. "Public file."
    Public { secret: Secret },
}
```

A bucket's `Manifest::shares` becomes a list of these. Membership and public-ness become the same primitive, distinguished only by `wrap`:

- Member identity = `Sealed` share targeting the root node.
- Subtree delegate = `Sealed` share targeting a non-root node.
- Public file/dir = `Public` share targeting that node.

No `PrincipalRole`. No `Manifest::public`. No bucket-level publish/unpublish. The "is X readable to whoever" question is answered by walking shares.

**Permission set (target v2):**
- `add_share(Share)` / `remove_share(share_id)` — requires a sealed share targeting the same node or an ancestor.
- `commit(new_head)` — requires a sealed share targeting root (write authority).
- Sync ops — unchanged, unauthenticated.

That's the whole permission surface. No publish endpoint.

### Decisions (20260524T015026Z thing2 — made unilaterally per user direction "make some choices, experiment")

**D1 — Granularity = exactly one node per Share, no recursion at the data-model level.**
A Public share targeting a `Dir` exposes that Dir's child-list (names + `NodeLink`s and their Link CIDs) but NOT any child's `NodeLink::Secret` — each child has its own random secret and needs its own Share. The CLI/API will offer a `--recursive` helper that fans out and creates a Public share per descendant; this stays out of the protocol layer. Rationale: matches the existing data model (independent per-node secrets in `mount/node.rs:96-99`); avoids ambiguous "what does a Dir Public share mean" semantics; makes the protocol invariant simple — *one Share, one node, one secret.*

**D2 — Public shares are gated by manifest signature, same as Sealed shares.**
To `add_share(Share{target, wrap})` for any wrap variant, the actor must hold a Sealed share whose target is `target` itself or one of its ancestors (so they already had the plaintext secret needed to produce the share). This is naturally enforced: you can't honestly produce a `Public{ secret }` payload without already having the secret. Manifest signature gates the mutation. No new permission machinery.

**D3 — Revoke = remove the share; key rotation is a separate explicit op.**
Removing a Public share unlinks it from the manifest but does not unmake the secret — copies in the wild remain readable. To actually revoke read access, the owner runs a *rotate* op: generate a new `NodeLink::Secret`, re-encrypt the underlying blob (or re-link), re-issue any Sealed shares for the node. Public shares are not auto-recreated on rotate. Document the semantic and move on; this matches the current bucket-secret rotation pattern in `mount_inner.rs:183-186`.

### Share struct sketch (target v2)

```rust
// crates/common/src/mount/share.rs (new file, replaces parts of manifest.rs)

/// Reference to a node in the mount DAG. Content-addressed.
pub type NodeRef = Link;  // Link is already the CID/content-address type

/// A grant of access to a single node's secret.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct Share {
    /// The node whose `NodeLink::Secret` this share unwraps.
    pub target: NodeRef,
    /// How the secret is wrapped.
    pub wrap: ShareWrap,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum ShareWrap {
    /// Encrypted to a recipient identity. Only that identity can unwrap.
    Sealed {
        recipient: PublicKey,
        ciphertext: SecretShare,  // existing X25519-sealed type
    },
    /// Plaintext secret. Anyone with the manifest can unwrap. "Public."
    Public {
        secret: Secret,
    },
}

impl Share {
    pub fn sealed(target: NodeRef, recipient: PublicKey, secret: &Secret) -> Self { /* X25519 seal */ }
    pub fn public(target: NodeRef, secret: Secret) -> Self { Share { target, wrap: ShareWrap::Public { secret } } }

    pub fn unwrap_for(&self, identity: Option<&SecretKey>) -> Option<Secret> {
        match &self.wrap {
            ShareWrap::Public { secret } => Some(secret.clone()),
            ShareWrap::Sealed { recipient, ciphertext } => {
                let sk = identity?;
                if sk.public() != *recipient { return None; }
                Some(ciphertext.decrypt(sk))
            }
        }
    }
}
```

### Path → secret resolution (target v2)

To read node at path `P` with optional identity `I`:

1. Resolve the manifest's root `NodeRef` → walk to `P`'s parent → find the `NodeLink` for `P`.
2. Need the parent's `NodeLink::Secret` to walk into the parent's Node body. So recurse: resolve up the chain until we find a node whose `NodeRef` matches the `target` of some `Share` in `manifest.shares` that we can `unwrap_for(I)`.
3. From that anchor, walk down: each step needs the next `NodeLink::Secret`, which lives *inside the parent Node body* (which we just decrypted using the previous secret).

So the access invariant becomes: **you can read node X iff manifest contains at least one Share you can unwrap whose `target` is an ancestor of X (or X itself).** Mirror role, publish flag, all gone — replaced by walking up looking for an unwrappable share.

### Worked example (20260524T015247Z)

Setup: Alice creates a bucket, adds Bob as a member, then publishes one file for Carol (a non-member with no shared keys).

```
t=0   Alice creates bucket
      manifest.head = root_node (CID R)
      root_node body (decrypts with secret S_R) contains:
          (empty, no children yet)
      manifest.shares = [
        Share{ target: R, wrap: Sealed{ recipient: Alice.pub, ciphertext: seal(S_R, Alice.pub) } }
      ]
      manifest signed by Alice

t=1   Alice writes /notes/intro.txt
      Alice generates fresh secrets S_notes (for the dir) and S_intro (for the file blob).
      root_node body now has:  "notes" -> NodeLink::Dir(L_notes, S_notes)
      notes_node body has:     "intro.txt" -> NodeLink::Data(L_intro, S_intro, …)
      Both bodies are stored encrypted-at-rest in blob storage under their parent's secret.
      No new Share entries needed — Alice already has S_R, which transitively unlocks everything.
      manifest re-signed by Alice.

t=2   Alice adds Bob (full membership)
      add_share(Share{ target: R, wrap: Sealed{ Bob.pub, seal(S_R, Bob.pub) } })
      Bob can now unwrap S_R and walk the whole tree.

t=3   Alice publishes /notes/intro.txt for Carol (Carol is not a member)
      add_share(Share{ target: L_intro, wrap: Public{ secret: S_intro } })
      Carol fetches the manifest (manifests are public artefacts) and the L_intro blob.
      Carol resolves the path: she cannot decrypt the root_node body (no Sealed share she can
      unwrap), so she cannot *walk* the path /notes/intro.txt. Instead she's given the
      content-address L_intro directly (via URL like
      https://hub.example/b/<bucket_id>/blob/<L_intro>).
      With the Public share for L_intro, she decrypts the blob using S_intro.
      → CONSEQUENCE: a public file is addressed by its Link, not its path. The hub
        gateway maps friendly URLs (/<bucket>/notes/intro.txt) to blob Links by walking
        the tree itself (the hub IS a member or has Sealed shares to the relevant dirs).
        For a non-member Carol with no path-walking ability, the hub serves as the namer.

t=4   Alice revokes /notes/intro.txt
      Option A (cheap): remove the Public share. Carol's existing copy of S_intro still
      works for the existing blob. Future fetchers without the share cannot decrypt.
      Option B (real revoke): rotate. Alice generates S_intro' , re-encrypts the file
      blob with S_intro' producing L_intro', updates the NodeLink in notes_node, and
      drops the Public share. Carol's old S_intro cannot decrypt L_intro'. The old
      L_intro blob can be garbage-collected from cooperating storage.
```

Key insight from the example: **Public shares grant access to a blob, not to a path.** Path naming requires walking the tree, which requires Sealed shares. The hub gateway sits in the middle — it's a member (Sealed-share holder) that translates paths to blob Links for non-members who only have Public shares. This is why the hub crate (T-002) is necessary even though Mirror role is gone: someone has to name things for the web.

### Rotate op spec

Single op: `rotate_node(path)`.

```rust
async fn rotate_node(&mut self, path: &Path) -> Result<()> {
    // Walk to the parent of the target. Requires Sealed share for an ancestor.
    let (parent_node, child_name) = self.resolve_parent(path).await?;
    let old_link = parent_node.links.get(child_name).ok_or(NotFound)?;
    let new_secret = Secret::generate();

    match old_link {
        NodeLink::Data(_, _, data) => {
            // Fetch the plaintext, re-encrypt under new_secret, store new blob.
            let plaintext = self.blobs_store.fetch_and_decrypt(old_link).await?;
            let new_link = self.blobs_store.encrypt_and_put(&plaintext, &new_secret).await?;
            parent_node.links.insert(child_name.into(),
                NodeLink::Data(new_link, new_secret.clone(), data.clone()));
        }
        NodeLink::Dir(_, _) => {
            // Re-encrypt the dir body (the Node struct itself).
            let dir_body = self.blobs_store.fetch_and_decrypt(old_link).await?;
            let new_link = self.blobs_store.encrypt_and_put(&dir_body, &new_secret).await?;
            parent_node.links.insert(child_name.into(),
                NodeLink::Dir(new_link, new_secret.clone()));
        }
    }

    // Drop any Share entries whose target was the old link.
    self.manifest.shares.retain(|s| s.target != *old_link);

    // Re-encrypt parent dir body (new NodeLink secret means parent body changes).
    // This cascades up to root, producing a new manifest.head.
    self.commit_chain_up_to_root(parent_node).await?;
    self.manifest.sign(&self.identity);
    Ok(())
}
```

Properties:
- Rotating a Dir cascades up to root (new Dir Link → parent's NodeLink changes → parent body changes → grandparent's NodeLink changes …). This is the same cascade as any write.
- Rotating a Data leaf does NOT touch siblings.
- After rotate, any previously issued Public/Sealed shares for the old Link are no longer in the manifest. If a member wants to keep sharing the rotated node, they re-issue a share targeting the new Link.

### Gateway-handler sketch (zim-hub or daemon http_server/gateway)

```rust
// Replaces http_server/gateway/*.rs and api/v0/bucket/version.rs
// Bucket id is from the URL.
// The hub holds Sealed shares (it's a member of every bucket it serves) so it
// can walk paths. Non-member web clients hit the hub, not the peer protocol.

async fn serve_path(bucket_id: BucketId, path: &str) -> Response {
    let mount = open_mount_as_member(bucket_id).await?;
    let node_link = mount.resolve_path(path).await?;  // walks the tree using our Sealed share

    // Is this node "public"? Look for a Public share targeting it.
    let public_share = mount.manifest.shares.iter()
        .find(|s| s.target == *node_link.link()
                  && matches!(s.wrap, ShareWrap::Public { .. }));

    match public_share {
        Some(_) => {
            let plaintext = mount.blobs_store.fetch_and_decrypt(node_link).await?;
            Response::ok(plaintext)
        }
        None => Response::not_found(),  // hub refuses to serve non-public nodes
    }
}
```

The hub's authority to *read* comes from being a member (Sealed share). Its authority to *serve* comes from finding a Public share. These are decoupled — the hub can read everything but only serves nodes the owner marked public. This is the desired "GitHub-style read-only public mirror" semantic without any Mirror role.

- Hub is a peer that joins each bucket as a member (Sealed share targeting root). It needs an identity key and a way to be added as a member — likely via the owner adding the hub's pubkey through the normal share-management flow.
- Hub's HTTP routes mirror the daemon's gateway, but it does the path-resolve internally and only serves Public-share-targeted nodes.
- WASM client path (factor-1): the hub serves the manifest JSON (public artefact) + blob CIDs. WASM client running in the browser can fetch blobs directly from the hub's blob endpoint and decrypt locally if it has a Public share. (No identity-server roundtrip needed for public files; for "logged-in" reads of non-public files, see factor-1 Google sign-in design — future work.)
