## Goal
Owner-side surface for managing viewer authorizations against a bucket. See T-001 `## Proposal (20260524T050253Z thing5)`.

## Acceptance
- [ ] CLI: `zim bucket viewer list-pending <bucket_id>`, `zim bucket viewer authorize <bucket_id> <viewer_pubkey>`, `zim bucket viewer deauthorise <bucket_id> <viewer_pubkey>`.
- [ ] HTTP: `GET /buckets/{id}/viewers`, `POST /buckets/{id}/viewers` (authorize), `DELETE /buckets/{id}/viewers/{pubkey}` (deauthorise).
- [ ] `authorize` adds the viewer's pubkey to `manifest.shares` with per-blob `Secret`s encrypted for the new key (same surface T-008 already uses for bucket membership).
- [ ] `deauthorise` removes the share and triggers re-encryption of touched secrets (clean break — no membership without re-key).
- [ ] `cargo build/test/clippy/fmt` all green.

## Out of scope
- zim-hub-side auth (T-001a).
- zim-wasm-side crypto (T-001b).
- Docs (T-001d).
- Sits next to T-016c (mirror management CLI) — natural batching.

  - **Endpoint shape deviation from acceptance**: spec said `GET /buckets/{id}/viewers`, `POST /buckets/{id}/viewers`, `DELETE /buckets/{id}/viewers/{pubkey}`. Implemented as flat `POST /api/v0/bucket/viewers/{verb}` to match the existing convention in `bucket/mod.rs` (every other endpoint is flat-route + bucket_id-in-body). REST-pure nested routing would require restructuring the whole bucket sub-router — bigger surface than fits T-001c. Functionally equivalent; the CLI doesn't notice.
  - **list-pending NOT IMPLEMENTED.** The pending-viewers list lives on the **hub** (per T-001 Decision 3 — viewers enrol at zim-hub via Google OAuth and the hub records pubkeys awaiting owner authorization). The owner-side CLI would need a `--hub <url>` flag and would call `GET /api/v0/identity/pending` on the hub. That hub endpoint is **part of T-001a** (thing3), still in flight. Replaced the trio with a `list` command that shows currently-authorized viewers from the local bucket manifest — useful for "which pubkeys currently have access?". When T-001a ships, a follow-up adds `list-pending --hub <url>`.
  - **Deauthorise re-key NOT IMPLEMENTED.** Acceptance asked for "clean break — no membership without re-key": after deauthorise, the removed viewer's pubkey can no longer decrypt **future** content. Today the deauthorise endpoint removes the share but does **not** rotate the per-node `Secret`s the viewer was sealed against. A viewer who cached blobs before deauthorise can still decrypt them. The endpoint logs a `tracing::warn!` and the CLI Display prints a note flagging the gap. **Follow-up: spawn T-001c-followup** for the re-key mechanic. Touches `Fs::save` semantics + manifest schema (need to know which nodes the deauthorised viewer was sealed against to rotate selectively); bigger than fits one tick.
