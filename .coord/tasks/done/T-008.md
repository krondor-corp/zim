## Goal
Replace whole-bucket publication (`Manifest::public` ships the entire bucket secret) with **per-file / per-folder publication**. The gateway (`zim-hub`) serves only files/folders that have been explicitly marked public; it never sees the bucket secret.

This is a design + proposal task in the same shape as T-006: produce the written target model and a delete/rewrite list. Sub-tasks for code edits will be spawned after.

Clean-break tenet applies — no compat with the existing `Manifest::public` plaintext-secret surface; that surface is removed.

## Proposal (20260524T022407Z thing2)

### Core insight

The existing data model already supports per-node encryption: every `NodeLink` carries its own random `Secret` (`zim-fs/src/fs/node.rs:96-99` — `NodeLink::Data(Link, Secret, Data)` and `NodeLink::Dir(Link, Secret)`). So per-file/per-folder publication needs no new crypto primitive — only a new manifest field that exposes specific nodes' existing secrets to the gateway.

`Manifest::public` (the whole-bucket plaintext secret) is **deleted**. In its place: a `published_set: Vec<PublicEntry>` field whose entries each grant the gateway access to exactly one node.

### Target data model

```rust
// crates/zim-fs/src/fs/published.rs (new file)

/// A grant of read access to a specific node in the tree, for the gateway/hub.
///
/// The hub never holds the bucket's owner secret — it reads only what
/// is named in the manifest's `published_set`.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct PublicEntry {
    /// Content-addressed Link of the node this entry publishes.
    /// For a Data node: the file blob's Link.
    /// For a Dir node: the directory body's Link.
    pub target: Link,

    /// Plaintext secret that decrypts `target`. This is the same value
    /// stored inside the corresponding `NodeLink::Secret` in the tree —
    /// copied out so the hub doesn't need to walk the tree to find it.
    pub secret: Secret,

    /// Friendly path the hub serves this entry under, e.g. "/blog/post.md".
    /// Independent of the in-bucket path; the owner picks. None ⇒ served
    /// only via /blob/<Link>.
    pub display_path: Option<String>,

    /// "How much" of this node is published.
    pub mode: PublicMode,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum PublicMode {
    /// File publication. `target` is a Data node Link; the hub decrypts
    /// and serves the file. (Equivalent for a Dir whose body lists no
    /// children — degenerate but allowed.)
    File,

    /// Folder publication. `target` is a Dir node Link. The hub decrypts
    /// the dir body using `secret`, then recursively walks descendants
    /// using each child's `NodeLink::Secret` from the body. Future
    /// children of this dir are included as long as the entry is kept
    /// current (see "Auto-republish on commit" below).
    Folder,
}
```

#### Manifest schema delta

```rust
// crates/zim-fs/src/fs/manifest.rs

pub struct Manifest {
    // KEEP:
    pub head: Link,                    // root node
    pub shares: …,                     // membership (Sealed shares to identities)
    pub signatures: Vec<Signature>,

    // ADD:
    pub published_set: Vec<PublicEntry>,   // hub-readable publication entries

    // DELETE:
    // pub public: Option<Secret>,         // whole-bucket plaintext secret — gone
}
```

The `published_set` is a flat list. One entry per published path. Manifests retain content-addressing — they're a public artefact and remain world-readable. What changes is that there is no longer a path from "I have the manifest" to "I can decrypt the bucket"; the manifest reveals only what is explicitly published.

### Cryptographic envelope

No new envelope. Each `PublicEntry.secret` is the same value that already lives in the tree as a `NodeLink::Secret`. The publication act is **copying that secret out into `published_set`**; the unpublication act is **removing the entry**. The owner has the secret because they hold the root Sealed share and can walk to any node; the act of publishing is just exposing one node's secret in a separately-addressable manifest field.

Cost: a published node's secret can be permanently exfiltrated from the moment of publication. Unpublication does not unmake the secret (this matches D3 from T-006 v2: revoke ≠ unmake). For true revocation, the owner runs `rotate_file(path)` / `rotate_folder(path)` which generates a new secret and re-encrypts the blob; see "Rotate semantics" below.

### Gateway access model

The hub (`zim-hub`) is **not a member** of the bucket. It does not hold any Sealed share. Concretely:

1. Hub fetches the manifest (public artefact; available via the standard sync protocol or directly from a peer that serves it over HTTP).
2. Hub indexes `manifest.published_set` by `display_path` → `PublicEntry`.
3. To serve `GET /<bucket_id>/<path>`:
   - If `path` matches an entry's `display_path` exactly:
     - `mode = File`: fetch `target` blob → decrypt with `entry.secret` → respond with bytes.
     - `mode = Folder`: fetch the dir body blob → decrypt with `entry.secret` → respond with an index listing.
   - If `path` is *inside* a published folder's `display_path`: walk descendants. The hub starts at the folder's dir node, decrypts its body with `entry.secret`, gets child `NodeLink`s. Each child `NodeLink` carries its own `Secret`. Hub continues walking using those child secrets. Stops at the target path; serves Data nodes; lists Dir nodes.
   - No match: 404.

What the hub cannot do:
- Walk into nodes that are not under any `PublicEntry`'s subtree.
- Decrypt the manifest's `shares` field's Sealed ciphertexts (it has no recipient identity key).
- Mutate the bucket.
- Discover sibling content in the bucket beyond what is reachable from a `PublicEntry`.

### Membership/publish ops set

#### Membership (unchanged from T-006)
- `add_member(identity, sealed_share)` — issue a Sealed share targeting root for a new member identity.
- `remove_member(identity)` — remove their Sealed share (does not retroactively block them; owners should also rotate the bucket secret if they want hard revocation, but that is a separate op of broader scope, out of T-008).

#### Publication
- `publish_file(path)` — resolve `path` to a Data NodeLink (`Link L`, `Secret S`). Append `PublicEntry { target: L, secret: S, display_path: Some(path), mode: File }` to `manifest.published_set`. Re-sign manifest.

- `unpublish_file(path)` — find entry whose `display_path == path && mode == File`; remove it. Re-sign.

- `publish_folder(path)` — resolve `path` to a Dir NodeLink (`Link L`, `Secret S`). Append `PublicEntry { target: L, secret: S, display_path: Some(path), mode: Folder }`. Re-sign.

- `unpublish_folder(path)` — symmetric.

#### Auto-republish on commit (sticky folder semantics)

When the owner commits a change that mutates a published node's Link (almost any write touching that node, since Links are content-addressed):

1. The new tree has a new Link for the affected node.
2. The corresponding `PublicEntry.target` would otherwise dangle (point at the old Link).
3. **Before signing**, the commit step iterates `published_set`, re-resolves each entry's `display_path` to the new Link/Secret, and updates the entry in place.
4. If a `display_path` no longer resolves (the path was renamed-out or deleted, see below), the entry is **pruned**.

This makes "publish_folder /blog" mean "serve `/blog`'s current contents on every commit going forward," which matches user intent.

#### Rename / move semantics

`mv /blog/post.md /blog/intro.md`:
- The Data node `NodeLink::Data(L_data, S_data, …)` keeps the same `L_data` and `S_data` (the file content didn't change).
- The dir body changes (BTreeMap key changes from "post.md" to "intro.md"), so the `/blog/` dir Link changes.
- Auto-republish step finds the `/blog/post.md` entry; re-resolving `/blog/post.md` fails (no such path now); the entry is pruned with a warning.
- Owner must run `publish_file /blog/intro.md` to re-establish.

`mv /blog/post.md /drafts/post.md`:
- File NodeLink stays the same.
- `/blog/`'s body changes; `/drafts/`'s body changes. Two dir Links change.
- Auto-republish re-resolves `/blog/post.md`; not found; pruned. Owner re-publishes at the new path.

This semantic is **strict on path**: the published path is a verbatim string match, not a tracked-content identifier. Tradeoff: simple, deterministic, surprising-but-defensible UX. An alternative would be a `track_by: ContentLink` mode that follows a file across renames; deferred as future work.

#### Delete semantics

`rm /blog/post.md`:
- Auto-republish step re-resolves `/blog/post.md`; not found; entry pruned.
- No error; CLI may print a warning.

`rm -r /blog/`:
- The `/blog/` Folder entry's `display_path` no longer resolves; pruned.
- All sub-published files under `/blog/` are also pruned (their display paths no longer resolve either).

### Rotate semantics

`rotate_file(path)`:
1. Generate fresh `S'` for the file.
2. Re-encrypt the file plaintext with `S'`; store as new blob with Link `L'`.
3. Update the parent dir body: replace `NodeLink::Data(L_old, S_old, data)` with `NodeLink::Data(L', S', data)`.
4. Cascade up: parent's Link changes, grandparent's body changes, etc., to root.
5. Auto-republish step refreshes any `PublicEntry` whose `display_path` resolves to this file: new `target = L'`, new `secret = S'`. (If owner wants the old `S` invalidated, they can also remove the entry first and re-publish after rotate, which leaves a window of unservedness.)
6. The old blob at `L_old` is now orphaned in the parent body but content-addressed storage may still hold it; that is a GC concern.

`rotate_folder(path)`:
- Generate fresh `S'` for the dir.
- Re-encrypt the dir body with `S'` → new dir Link `L'`.
- Cascade up.
- Auto-republish refreshes the Folder entry's target+secret.
- Crucially, this rotates only the **folder body** — the children's secrets stay unchanged. To rotate everything under the folder, run `rotate_folder` recursively at the leaves first, then at intermediate dirs, then at the root.

### Coordination — T-012 zim-wasm envelope JSON shape

Added 20260524T024508Z thing2. thing5's T-012 proposal defines a JS-facing `decryptBlob(envelopeJson, ciphertext)` that assumes the envelope carries a Secret *sealed for the viewer's pubkey*. That maps to the **member-viewer/logged-in reads** path (the "future work" item in this proposal), not the **public-files** path that T-008's `PublicEntry` directly enables.

Two envelope shapes are needed, with a single JSON discriminator the WASM client branches on:

```json
// Public file: anonymous viewer; secret is plaintext.
{ "kind": "public", "secret": "<hex>", "nonce": "<hex>" }

// Sealed for a member identity: viewer must have their identity key loaded.
{ "kind": "sealed", "share": "<hex>", "nonce": "<hex>" }
```

For T-008's gateway path: the hub serializes each `PublicEntry` into the `public` envelope shape and ships it alongside the ciphertext. Concretely, the gateway response for `GET /<bucket>/<published-path>` carries:
- Body: encrypted blob bytes from `target` Link.
- Header (or sidecar JSON): `{ "kind": "public", "secret": <PublicEntry.secret hex>, "nonce": <Manifest's AEAD nonce for this blob> }`.

The `sealed` shape lands when T-001's identity-key path arrives; until then, zim-wasm only needs to implement the `public` branch.

**For thing5 (T-012)**: please make `decryptBlob`'s envelope a tagged union from day one (even if only `public` is implemented v1) so future addition of `sealed` is non-breaking. The `loadKeyFromSession` function can stay in the v1 API as a no-op precondition for the sealed branch.

**For T-008b executor**: when wiring the gateway handler, the response shape for the encrypted-blob response must match this envelope schema. Suggested location for the shared serde type: a new `crates/zim-types/src/envelope.rs` or fold into `zim-fs` and re-export. Pick at implementation time.

### Coordination — Relay endpoint interaction (20260524T182506Z thing2)

T-008's `publish_file`, `unpublish_file`, `publish_folder`, `unpublish_folder`, and `rotate_*` ops are all manifest mutations (add/remove/update entries in `published_set`, re-sign manifest). From the Relay protocol design (`broadcast/20260524T182033Z-thing2-relay-role-dialable-shares-protocol-design.md`), ANY signed manifest mutation arriving at the hub's Relay endpoint (`POST /api/v0/buckets/{id}/append`) is validated identically: check signature against `manifest.shares`, check lineage against current head, persist, broadcast.

This means:
- **Browser-side publish/unpublish/rotate is free** once the Relay endpoint lands. The browser computes the new manifest (adding/removing PublicEntry), signs it with the web-key, POSTs it. No separate publish API needed on the hub. The T-008b touchpoints for `http_server/api/v0/bucket/files/publish.rs` etc. become **CLI-side and daemon-side only** (for the owner's own device). The web path goes through Relay.
- **No special-case in the Relay handler** for T-008's operations. The handler is mutation-agnostic — it validates signature + lineage and persists.
- **T-008b's gateway handler** (which SERVES published content to anonymous readers) is a separate read path, unaffected by Relay. Gateway reads `published_set` from the persisted manifest state and serves accordingly.

For the T-008b executor: you don't need to duplicate the publish/unpublish API endpoints on the hub for web-key users. Relay covers it. The hub-side explicit endpoints (`POST /api/v0/buckets/{id}/files/publish` etc.) are a convenience surface for the owner's daemon/CLI — not the browser path.
