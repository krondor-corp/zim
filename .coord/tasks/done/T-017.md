## Goal
Extend the T-001 identity-vault design with:
1. **Device model** — a user has N devices. Only the **web device** (zim-hub session) keeps its key in the hub-as-vault. All other devices (CLI, mobile, desktop) generate keypairs locally and the private key NEVER leaves the device. Each device is independently revocable.
2. **Ed25519-signed JWT auth for zim-hub's API** — each device's key signs JWTs that authenticate non-browser API calls (CLI, MCP, third-party tools).

Design-only first (proposal in this task's `## Proposal` section, same shape as T-001/T-008/T-016). Sub-tasks for impl spawn after.

## Binding constraints (from user)

- **Only the web device needs a password.** Hub auto-provisions the web device's keypair on first OAuth login. The password unlocks the encrypted blob in the vault (current T-001 design — that flow is for the web device specifically).
- **All other devices' keys live on-device.** No hub-side vault entry. Hub stores only the device's pubkey + metadata.
- **The hard problem is bootstrapping a new device** — see "Device bootstrap" below. This is the design crux.

## Schema shape (constraint-derived)

```sql
-- one row per user
CREATE TABLE users (
    google_sub      TEXT PRIMARY KEY,
    google_email    TEXT NOT NULL,
    created_at      INTEGER NOT NULL
);

-- one row per device (incl. the web device)
CREATE TABLE devices (
    id              TEXT PRIMARY KEY,        -- uuid
    google_sub      TEXT NOT NULL REFERENCES users(google_sub),
    public_key      TEXT NOT NULL UNIQUE,    -- ed25519 pubkey hex
    label           TEXT NOT NULL,           -- user-supplied: "MacBook", "Phone", "Web"
    kind            TEXT NOT NULL,           -- "web" | "cli" | "mobile" | "desktop"
    created_at      INTEGER NOT NULL,
    last_used_at    INTEGER NOT NULL
);

-- ONLY web devices: the encrypted-blob-on-hub vault entry
-- (key has nowhere else to live; non-web devices keep keys locally)
CREATE TABLE web_device_vault (
    device_id       TEXT PRIMARY KEY REFERENCES devices(id),
    encrypted_blob  BLOB NOT NULL,
    salt            BLOB NOT NULL,
    kdf_params      TEXT NOT NULL
);
```

(Adjust as design requires; this is the rough shape.)

## Why these are coupled

A device model produces JWT signers naturally — each device registers a keypair, that keypair signs JWTs. Schema becomes `(google_sub, device_id)` instead of just `google_sub`. Revocation = remove the row + the device's JWTs stop verifying.

### Device bootstrap (the hard problem)

How does device #2 get its pubkey into the hub's `devices` table, given the key never leaves device #2?

Options to evaluate (pick one + describe the flow):
- [ ] **OAuth-on-new-device + push approval to existing**: new device does Google OAuth. Hub sees "known google_sub, unknown pubkey", emits a "pending device approval" record. Hub pushes (SSE/Datastar) to existing logged-in web sessions: "Approve $label from $ip?" User clicks approve on existing device — existing device's key signs an approval payload `(new_device_pubkey, expiry)` and POSTs to hub. Hub verifies signature, promotes `pending` to `devices` row.
- [ ] **QR code pairing**: existing device displays QR encoding a short-lived one-time approval token + hub URL. New device scans, generates keypair, POSTs `(new_pubkey, label, token, signature_from_token)` to hub. Hub verifies token, registers.
- [ ] **CLI flow**: `zim hub register --hub https://hub.example.com` opens browser (PKCE-like flow). User logs in on web (if not already). Web device approves. CLI receives the device-id + minted JWT, writes to `~/.config/zim/hub-token`.
- [ ] **First device exception**: on very first login, the web device IS the first device — no other device exists to approve it. So device-1 is auto-approved by virtue of being the user's first OAuth login. Device-2+ requires existing-device approval.
- [ ] **Lost all devices**: if user loses every device, recovery = Google OAuth on a fresh browser. New web device is created (no approval needed because user re-proved Google ownership). All previous devices' keys are effectively orphaned (still listed, but no path to use them without prior session); user revokes them from the new web device.

### JWT signer API auth
- [ ] JWT algorithm: EdDSA (ed25519 native, RFC 8037). Pick this — matches the key type we already have.
- [ ] JWT claims: standard `iss` / `sub` / `aud` / `exp` / `iat` / `nbf`, plus `device_id` and `google_sub`. What else?
- [ ] JWT lifetime: short (5min, like API tokens) vs medium (1h)? Refresh mechanism?
- [ ] Where does the signing happen? In zim-wasm if browser-originated, in a `zim` CLI command for headless clients (`zim hub login → cache token in ~/.config/zim/hub-token`).
- [ ] Hub-side verification: hub stores all device pubkeys, looks up by `device_id` in JWT header, verifies EdDSA signature. Fast path.
- [ ] Where do JWT-auth'd routes live? `/api/v0/*` — currently this is largely empty; what gets exposed first? (Bucket list, file read, publish ops, MCP tool calls?)
- [ ] Browser session vs JWT: do browser pages still use the signed cookie, with JWT only for programmatic API? Or unify on JWT for everything? Recommend keep them separate — cookie for browser pages (CSRF-protected via existing CSRF tooling), JWT for stateless API.
- [ ] CLI flow: `zim hub register --hub https://hub.example.com` (browser flow to mint a new device + cache its token) vs out-of-band paste-a-token-from-browser.

## Proposal (20260524T165530Z thing5)

### Headline pattern — Web device is hub-vault; every other device is **on-device keys, hub-stored pubkey only**

Extends T-001's identity-vault pattern with a **device layer** on top:

- **Web device** (browser sessions): keypair lives in `web_device_vault` (hub-side encrypted blob, viewer-password-derived KEK in zim-wasm). Current T-001 / T-001b crypto **unchanged**.
- **All other devices** (CLI / mobile / desktop): keypair generated on-device, private key **never leaves**. Hub stores only `(device_id, public_key, label, kind, ...)` metadata.
- **JWT API auth** is a natural consequence: each device's key signs short-lived EdDSA JWTs for non-browser API calls. Hub verifies signature by looking up the device's pubkey.

The trust model collapses cleanly: every device authenticates to the hub by **proving possession of its private key** (either via Argon2-unlock + WASM-sign for web, or direct sign for native). The hub never holds non-web private keys. Lost device = revoke its row, JWTs stop verifying.

### Decision 1 — Schema (confirm + extend the rough shape)

Three tables; binding shape (matches what orch sketched):

```sql
CREATE TABLE users (
    google_sub      TEXT PRIMARY KEY,
    google_email    TEXT NOT NULL,
    created_at      INTEGER NOT NULL,
    last_active_at  INTEGER NOT NULL
);

CREATE TABLE devices (
    id              TEXT PRIMARY KEY,        -- uuid v4
    google_sub      TEXT NOT NULL REFERENCES users(google_sub),
    public_key      TEXT NOT NULL UNIQUE,    -- ed25519 pubkey hex (64 chars)
    label           TEXT NOT NULL,           -- "MacBook Pro", "Phone", "Web (Chrome)"
    kind            TEXT NOT NULL,           -- "web" | "cli" | "mobile" | "desktop"
    created_at      INTEGER NOT NULL,
    last_used_at    INTEGER NOT NULL
);
CREATE INDEX idx_devices_google_sub ON devices(google_sub);
CREATE INDEX idx_devices_public_key ON devices(public_key);

-- ONLY web devices: encrypted-blob-on-hub vault entry.
-- Non-web devices' private keys live on-device; no row here.
CREATE TABLE web_device_vault (
    device_id       TEXT PRIMARY KEY REFERENCES devices(id) ON DELETE CASCADE,
    encrypted_blob  BLOB NOT NULL,
    salt            BLOB NOT NULL,
    kdf_params      TEXT NOT NULL            -- JSON: argon2id params (current: m=19456,t=2,p=1)
);

-- Pending devices awaiting approval from an existing device.
-- See Decision 4 (bootstrap).
CREATE TABLE pending_devices (
    id              TEXT PRIMARY KEY,        -- uuid v4
    google_sub      TEXT NOT NULL REFERENCES users(google_sub),
    public_key      TEXT NOT NULL,           -- ed25519 pubkey hex from the requesting device
    label           TEXT NOT NULL,           -- user-supplied or UA-derived
    kind            TEXT NOT NULL,           -- "cli" | "mobile" | "desktop" | "web"
    requested_at    INTEGER NOT NULL,
    expires_at      INTEGER NOT NULL,        -- 10 min after request, sweeper deletes expired rows
    request_ip      TEXT,                    -- shown to approver for "is this you?" sanity
    request_ua      TEXT
);
CREATE INDEX idx_pending_devices_google_sub ON pending_devices(google_sub);
```

`ON DELETE CASCADE` on the vault FK means revoking a web device row automatically drops its vault entry. Non-web devices have no vault row to drop; just delete `devices` row and JWTs from that device stop verifying.

### Decision 2 — Web-device auto-provisioning (Recommended: client-side)

On first OAuth login:
1. Hub creates `users` row (idempotent on `google_sub`).
2. Hub renders the `/enrol` page (Datastar) with the web-device label pre-filled from User-Agent ("Web (Chrome on macOS)") — editable.
3. Browser calls `zim_wasm.generateKey()` → 32-byte pubkey in JS, secret stays in WASM session.
4. Viewer enters unlock password (T-001 flow). Browser calls `zim_wasm.encryptKeyBlob(password)` → `{encryptedBlob, salt, publicKey}`.
5. Browser POSTs `(label, kind="web", encryptedBlob_hex, salt_hex, kdf_params_json, publicKey_hex)` to `/api/v0/identity/enrol`. Hub inserts a `devices` row + a `web_device_vault` row.
6. Hub returns the new `device_id`; browser stores it in the session cookie alongside `google_sub`.

**Client-side** keypair generation maintains T-001's load-bearing property: hub never sees the plaintext key. zim-wasm's surface (T-001b) already supports this; no new exports needed for web enrolment.

### Decision 3 — Listing + revocation UI (`/account/devices`)

Datastar page (thing3's `crates/zim-hub/templates/pages/account/devices.html`):

| Label | Kind | First Seen | Last Used | Action |
|---|---|---|---|---|
| MacBook Pro | cli | 2026-05-21 | 2 min ago | [revoke] |
| Web (Chrome) | web | 2026-05-20 | now (this session) | [revoke] |
| Phone | mobile | 2026-05-22 | 1 hour ago | [revoke] |

Click [revoke] → Datastar action → POST `/api/v0/identity/devices/{id}/revoke` → hub deletes the row. If revoking the current session's device, hub also clears the session cookie ("you've signed yourself out"). If the revoked device is the only web device for a user, hub keeps the user row (other devices can still authenticate via JWT — user can sign in via Google again to mint a fresh web device).

Pending devices appear in a separate section:

| Label | Kind | Requested | From IP | Action |
|---|---|---|---|---|
| Phone | mobile | 30 sec ago | 192.0.2.10 | [approve] [reject] |

Click [approve] → browser calls `zim_wasm.signApproval(pending_device_id, new_pubkey, expiry_unix)` → POST signed payload to `/api/v0/identity/pending/{id}/approve` → hub verifies signature against the approving device's pubkey, promotes the pending row to `devices`. See Decision 4.

### Decision 4 — Device bootstrap (the hard problem)

**Primary flow: OAuth-on-new-device + push approval.**

Rationale: matches user expectation (sign in on the new device → get prompted on existing one), uses Google OAuth as the *identity* proof (hub trusts Google that this person owns `google_sub`), uses the existing device's key as the *approval* signing authority (only someone with private-key access to an approved device can promote a pending row). Two-factor: Google OAuth establishes identity; existing-device signature establishes "yes, this person on the new device is the same as me on this trusted device".

End-to-end (mobile/desktop example):
1. User opens zim-hub on phone, hits `/login`.
2. Standard Google OAuth PKCE → hub establishes a session keyed by `google_sub`.
3. Hub looks up `devices WHERE google_sub = $1 AND kind != 'web'`. None for this phone.
4. Hub renders `/enrol/device` (Datastar): "Hi! New device for $email. We need to register it. Label: [Phone]. Kind: [mobile]. Submit."
5. On submit: browser/native client generates an ed25519 keypair locally (WASM if browser; native `ed25519-dalek` if mobile app). POST `(google_sub, label, kind, public_key_hex, request_ua)` to `/api/v0/identity/pending`. Hub inserts a `pending_devices` row, returns `pending_id`.
6. Phone polls (or opens SSE to) `/api/v0/identity/pending/{pending_id}/wait` for approval.
7. Hub pushes a `device_approval_request` SSE frame to every active web device session for this `google_sub`: `{ pending_id, label, kind, request_ip, request_ua, requested_at }`.
8. Existing web device's Datastar page shows the pending-device card with [approve] / [reject] buttons.
9. User clicks [approve] on existing device. Browser calls `zim_wasm.signApproval(pending_id, new_pubkey, expiry_unix)` → returns ed25519 signature. POST `(pending_id, expiry_unix, signature_hex)` to `/api/v0/identity/pending/{pending_id}/approve`.
10. Hub verifies signature against the approving web-device's pubkey, deletes the `pending_devices` row, inserts a `devices` row, sends success SSE to the waiting phone.
11. Phone receives success, caches its private key + `device_id` locally. From this point onward it signs its own JWTs.

**Secondary flow: QR pairing** (for offline / no-existing-web-session case):
- Existing web device shows a QR code encoding `(hub_url, one_time_token, expires_at, approving_device_id)`.
- New device scans, generates keypair, POSTs `(label, kind, public_key, one_time_token, signature_of_token_with_new_key)` to `/api/v0/identity/pair/qr`.
- Hub verifies the one_time_token matches an active pairing session + verifies the new device proved control of the new key + asks the existing web device to confirm via the same SSE channel as the primary flow.
- Out-of-v1; mention as future capability.

**CLI flow** (headless): `zim hub register --hub https://hub.example.com`.
- Opens browser to a `/auth/cli-register?cli_callback=http://127.0.0.1:<random_port>/cb` URL.
- User logs in (or existing session is used). User chooses label/kind ("My Laptop" / "cli").
- Browser asks for [approve] via the same primary flow.
- On approval, browser POSTs `(device_id, expiry, encrypted_signing_key)` to the local CLI's `<cli_callback>` over loopback. CLI receives it, writes `~/.config/zim/<hub>/device.key` (locked-down permissions) + `~/.config/zim/<hub>/device-id`.
- From there, CLI signs JWTs locally for any API call.

**First-device exception**: device-1 is auto-approved by virtue of being the user's first OAuth login (`devices` WHERE `google_sub = $1` has 0 rows → bypass pending step, insert directly). Documented as an explicit branch in the enrolment handler.

**Lost-all-devices recovery**: Google OAuth on a fresh browser. Hub sees `google_sub` exists in `users` but the requesting browser has no session cookie. Goes through the same first-device-like flow: creates a NEW web device, NEW vault entry (user picks a NEW password — the OLD encrypted blob is unrecoverable because the OLD password is lost). All previous devices' rows remain in `devices`; user can revoke them from the `/account/devices` page once signed in.

### Decision 5 — Effect on T-008 / T-016 — per-device shares (Option c)

Picking **(c) per-device shares**: each device gets its own `Share` in the manifest's `shares` map. Owner-side `zim viewer authorize <google_sub>` queries the hub's `devices` table for the target user, enumerates their pubkeys, and creates one `Share::new_owner(SecretShare::new(&secret, &device_pubkey)?, device_pubkey)` per device.

Why not (a) per-device-explicit: it's the same thing, just with more steps on the owner's side. (c) abstracts "authorize this user" as "authorize all their currently-registered devices, plus listen for new device additions and re-authorize incrementally".

Why not (b) per-user (hub re-issues): the hub would need to hold a secret to re-encrypt per device — violates the property that hub never holds bucket secrets.

**New device → re-authorization round-trip**:
- New device registered via Decision 4 flow.
- Hub emits a `device_added` event (could be a Datastar SSE or a hub→owner push, depending on whether the owner has a session open).
- For each bucket the user is authorized for, the OWNER (who holds the bucket secret) needs to sign + append a new manifest version that includes the new device's `Share`.
- Owner runs `zim bucket viewer authorize <bucket> <google_sub>` (or the per-bucket auto-re-auth wakes up on event); enumerates the user's devices via hub API, creates per-device shares, appends manifest.
- Until the owner does this, the new device authenticates to the hub (JWT works) but cannot decrypt sealed envelopes for buckets it wasn't pre-authorized for. zim-wasm's `decryptBlob` returns "share recover failed" for the unauthorized device — the user sees a clear error rather than mystery decryption failures.

**`Manifest::shares` semantics**: a single `google_sub` can correspond to multiple `(pubkey -> Share)` entries. The existing `BTreeMap<String /* pubkey hex */, Share>` shape supports this already; no schema change. Adds a soft assumption: "the same identity controls all entries with the same downstream user binding" — but the hub-side `devices` table is the source of truth on which pubkeys belong to which user.

**No T-008a/b code changes needed**. Owner-side enumeration logic is new (lives in zim-peer CLI under T-017c). The existing `Manifest::add_share` is called once per device.

### Decision 6 — JWT signer / verifier (EdDSA over device key)

**Algorithm**: `EdDSA` per RFC 8037 (`alg: "EdDSA"`, `crv: "Ed25519"`, `kty: "OKP"`). Matches the ed25519 keys we already have everywhere.

**JWT structure**:
- Header: `{ "alg": "EdDSA", "kid": "<device_id>" }` — `kid` is the device UUID, used by the hub's verifier to look up the corresponding pubkey in the `devices` table.
- Payload claims:
  - `iss`: the device's pubkey hex (or `device_id`; same info, pick one — recommend `device_id` for shorter tokens).
  - `sub`: `google_sub` of the device's owning user.
  - `aud`: hub canonical URL (e.g. `https://hub.example.com`) — verifier rejects tokens not targeting this hub.
  - `iat`: issued-at unix timestamp.
  - `nbf`: not-before; usually `iat - 30` to absorb clock skew.
  - `exp`: expiry; `iat + 300` (5 minutes — short, no refresh needed since the device just signs another).
  - `jti` (optional): jwt id for one-time-use semantics on sensitive ops; could be skipped in v1.

**Lifetime**: short (5 min). Because each device has its own signing key, the device can mint a fresh JWT whenever the previous one is about to expire — there's no "refresh token" concept needed. The classic refresh-token pattern exists to keep the signing key (bound to OAuth provider) off the client; in our model the signing key IS the device's identity, so the client always has it.

**Where signing happens**:
- **Browser**: zim-wasm gets a new export `signJwt(claims_json: string) -> string` (T-001b extension). Datastar page calls it for any client-initiated API request that targets `/api/v0/*` (vs HTML pages which use the session cookie).
- **CLI** (headless): native `ed25519-dalek` sign using the key in `~/.config/zim/<hub>/device.key`. New `zim_jwt` helper module in zim-peer's CLI crate. CLI commands like `zim ls`, `zim cat` get a `--hub` flag that flips them to JWT-auth'd HTTP calls instead of local-IPC.

**Hub-side verification** (thing3's territory):
- Middleware on `/api/v0/*` routes.
- Parse JWT header, extract `kid`, look up `devices.public_key WHERE id = kid`.
- Verify EdDSA signature with that pubkey.
- Check `aud` matches hub URL, `exp > now`, `nbf < now`.
- Inject `sub` (google_sub) and `device_id` into request extensions for downstream handlers.
- On verification failure: 401 with a clear error code (`invalid_signature`, `expired`, `device_revoked`, `wrong_audience`).

**Browser session vs JWT — keep separate**:
- HTML pages: signed cookie (existing T-001a / thing3 surface). CSRF tooling on POST forms.
- `/api/v0/*` JSON endpoints: EdDSA JWT in `Authorization: Bearer <token>` header.
- The two coexist; a browser page that does a JS-initiated POST to `/api/v0/foo` calls `zim_wasm.signJwt({...})` and sends the JWT.

### Decision 7 — Migration from T-001 (clean-break, single-step)

T-001a (thing3, currently mid-flight, uncommitted) ships an `identity_keys (google_sub PRIMARY KEY, encrypted_blob, salt, kdf_params, public_key, created_at, last_used_at)` table. Migration replaces this with the four tables in Decision 1.

- **(a)** thing3 lands T-001a as-is, then a T-017a migration adds a new SQL migration file that creates `users` / `devices` / `web_device_vault` / `pending_devices`, copies each `identity_keys` row → `users (google_sub, email)` + `devices (id=uuid_v4, kind='web', label='Web', public_key)` + `web_device_vault (device_id, encrypted_blob, salt, kdf_params)`, then drops `identity_keys`.
- **(b)** Coordinate with thing3 so T-001a is amended to ship the T-017 schema from the start — no `identity_keys` table ever lands, the four new tables go in directly. **Cheaper** if T-001a hasn't been committed yet (thing3's note says T-001a is mid-flight).

**Recommended: (b).** Specifically: thing3 keeps their T-001a session-cookie + Google OAuth + identity-vault endpoint code; the only differences are (i) two more tables in the migration SQL, (ii) the enrolment endpoint creates rows in `users` + `devices(kind='web')` + `web_device_vault` instead of one row in `identity_keys`, (iii) the unlock endpoint joins through `devices` (filtered to `kind='web'`) to find the vault entry. Coordination message to thing3 covers the diff.

### Decision 10 — Explicit non-goals

- WebAuthn / FIDO2 device alternative — future direction (T-001 Decision 7 also flagged this).
- Multi-hub device sharing — explicit non-goal.
- Federated identity beyond Google — T-001 Decision 7 also flagged this.
- "Refresh token" mechanism — not needed; devices sign on demand.
- Cross-device key sharing (e.g. "send my Phone key to my Laptop") — explicit non-goal; each device is independent.
- JWT revocation list — by design, JWTs are short-lived (5 min) and verifier looks up `devices` row each verify; revoking a device removes its row → all its JWTs immediately stop verifying. No separate revocation list needed.
