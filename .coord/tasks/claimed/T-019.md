## Goal

Two structural changes that unblock clean dependency layering and reduce build overhead:

1. **`crates/zim-core/` leaf crate** — shared abstractions everyone depends on.
2. **rusqlite replaces sqlx in the daemon** — lighter weight for non-web-server usage.

## Problem 1 — No clean layer for shared abstractions

Current DAG has sideways dependencies driven by type placement, not conceptual ownership:

- `zim-fs → zim-store` because `Link`, `Hash`, `BlockEncoded`, `BlobsStore` live in zim-store.
- `zim-protocol → zim-store` for the same types.
- `zim-fs → zim-crypto` for keys.

The filesystem doesn't conceptually depend on "storage" — it depends on content-addressing primitives (Link, Hash) and a blob-store trait. These are shared abstractions that belong in a leaf crate.

### Target: `zim-core`

```
crates/zim-core/    # NEW leaf crate
├── src/
│   ├── lib.rs
│   ├── link.rs        # Link, Hash, Cid, BlockEncoded, DagCborCodec (from zim-store/linked_data/)
│   ├── blob_store.rs  # BlobStore trait (extracted from zim-store's BlobsStore concrete impl)
│   └── iroh.rs        # iroh re-exports (PublicKey via zim-crypto, NodeAddr, Endpoint, etc.)
```

New DAG:

```
zim-core: leaf (iroh-blobs Hash/Cid types, Link, BlobStore trait)
zim-crypto → zim-core (or stays independent if we keep key types separate)
zim-store → zim-core (BlobsStore implements BlobStore trait from core)
zim-fs → zim-core, zim-crypto
zim-protocol → zim-core, zim-fs, zim-crypto
zim-peer → everything above
zim-hub → everything above + zim-peer
```

The key win: `zim-fs` no longer depends on `zim-store`. It depends on `zim-core` for Link/Hash and on a `BlobStore` trait. The concrete `BlobsStore` (iroh-blobs + SQLite) stays in `zim-store`.

### Migration steps

1. Create `crates/zim-core/` with `Link`, `Hash`, `BlockEncoded`, `DagCborCodec`, `Cid`, `CodecError`, `LinkedData`, `multibase` — moved from `zim-store/src/linked_data/`.
2. Define a `BlobStore` trait in `zim-core` (async `get`, `put`, `stat`, `get_cbor`). `BlobsStore` in `zim-store` implements it.
3. `zim-fs` switches from `zim-store::linked_data::*` → `zim_core::*` and from `zim_store::BlobsStore` → `dyn BlobStore` (or generic `B: BlobStore`).
4. `zim-protocol` same switch.
5. `zim-store` depends on `zim-core`, removes `pub mod linked_data` (re-exports from core for compat if needed, or clean break).
6. Update root `Cargo.toml` workspace members.
7. Single green checkpoint: `cargo build && cargo test && cargo clippy -- -D warnings && cargo fmt -- --check`.

## Problem 2 — sqlx is too heavy for the daemon

sqlx brings:
- Compile-time query checking (sqlx-macros) — ~15s build overhead.
- Async connection pool — overkill for a single-connection SQLite daemon.
- Migration framework — nice but heavy for the daemon's simple schema.

The daemon's SQLite usage (bucket log, FUSE mounts, sync targets, bucket status) is simple CRUD. `rusqlite` with `tokio::task::spawn_blocking` for the few async callsites is lighter and faster to compile.

**sqlx stays in zim-hub** — the web server's connection pool, compile-time checked queries, and migration framework justify the weight there.

### Migration steps

1. Add `rusqlite` to workspace deps. Add to `zim-peer/Cargo.toml`.
2. Rewrite `crates/zim-peer/src/database/sqlite.rs` (the connection wrapper) to use `rusqlite::Connection` wrapped in `Arc<Mutex<>>` (or `tokio::sync::Mutex` for async).
3. Rewrite each query file (`bucket_log_provider.rs`, `bucket_queries.rs`, `bucket_status_queries.rs`, model files) from sqlx query macros to rusqlite `conn.execute` / `conn.query_row` / `conn.prepare`.
4. Replace sqlx migrations with a simple `CREATE TABLE IF NOT EXISTS` block run on connection open (rusqlite's `conn.execute_batch`).
5. Remove `sqlx` from `zim-peer/Cargo.toml`.
6. Verify `zim-hub` still uses sqlx independently (no cross-contamination).
7. Single green checkpoint.

## Sequencing recommendation

Do zim-core first (additive — new crate, move types, update imports). Then rusqlite (replace-in-place, touches every query). Both are single-PR-sized if the implementer is disciplined about not scope-creeping.

## Out of scope

- Renaming existing crates.
- New features.
- zim-hub database changes (stays sqlx).
- Protocol redesign.
